# Changelog

## 0.53.0 — 2026-10-29

Added:

- Trackpad swipes between pages, as browsers go back and forward. `on_history_swipe` (on `Element` builders and every component) gets a `HistorySwipeEvent` with a `direction` (`HistoryDirection::Back` for fingers to the right, `Forward` to the left) when two fingers that moved across the window sideways lift: far enough (120 logical pixels), mostly sideways (twice as far as up or down), and without a scroll container moving with them or a scroll handler preventing their default, so horizontal scrolling is unchanged and a sideways list at its edge lets the next swipe through. The event goes to the elements under the pointer, innermost first, until one stops its propagation. The momentum after a swipe is never a second one, and a swipe that interrupts that momentum still counts. Mouse wheels (scrolls without phases) and lurq's synthetic input make none. On macOS the swipes follow System Settings › Trackpad › "Swipe between pages" with two fingers (`NSEvent.isSwipeTrackingFromScrollEventsEnabled`, read as each gesture starts); set to three fingers only, AppKit sends a swipe event winit does not report, and no swipe is recognized. Other platforms report no scroll phases and have no swipes yet. lurq's `Router` does not follow swipes by itself: call `RouterHandle::back` / `forward` from `on_history_swipe`. `Tree::set_history_swipes` (hidden) turns the recognizer on in tests.

## 0.52.1 — 2026-10-29

Fixes:

- A screenshot of a macOS window nobody could see never completed. While the window is occluded (its application hidden, the window minimized or fully covered) Metal hands out no drawable and wgpu's `get_current_texture` answers `Occluded`, so the frame the capture waited for was skipped, and the next frame without a capture failed it as superseded: `WindowHandle::screenshot` wrote nothing and MCP `lurq_screenshot` answered "superseded before a frame was rendered". When the surface gives no texture and a capture waits, the wgpu renderer now draws that frame into a texture of the surface's size and format, takes the capture from it and presents nothing. Frames without a capture are still skipped while the window cannot be seen.

## 0.52.0 — 2026-10-28

Added:

- Styled text inputs, with the `markdown` feature. `TextInput::spans(Signal<Vec<StyledSpan>>)` makes an input edit bold, italic, inline code, strikethrough and links over its plain `Signal<String>` value, as UTF-8 byte ranges the app owns: the input draws the runs with the new theme roles `ThemeTextMarks` (`Theme::text_marks`, `set_text_marks`), moves them with every edit (typing, deleting, cut, paste, input method composition), keeps them in the same undo history as the text and writes them back. Typed text takes the style of the text before the caret, except that a link does not grow past its end. `TextInputController` gains `toggle_mark`, `set_mark`, `set_link`, `set_pending_style` (the style of the next typed text, for Ctrl+B while typing), `selection_style` (all, some or none per mark, for a toolbar), `styled_text`, `selected_styled_text` and `replace_selection_styled` (a paste handler's parsed spans). `TextInput::on_styled_change` reports every change the input makes as a `StyledChange` (the `StyledEdit`, the spans shared rather than copied, and the text on demand), `copy_format` sets what Ctrl+C copies from the styled selection (such as Markdown), and `on_link_click` reports a link clicked with Ctrl (Cmd on macOS). `TextInputHandle::copied_text` tells what Ctrl+C would copy. See the *Styled text inputs* guide and `examples/styled_editor.rs`. Plain inputs are unchanged.

Performance:

- A decorated input (input tokens, styled spans) without padded tokens no longer builds the cluster index padded rows need, about 40% less layout time for a long paragraph.
- A wrapped decorated input lays out a paragraph at a time and keeps each paragraph's layout, so an edit lays out only the paragraph it changed. Justified text and single-line inputs still lay out whole.
- A long left-to-right paragraph of a decorated input is shaped in chunks cut after spaces at places its own words choose; each chunk is kept, so an edit shapes only the chunk it changed. The paragraph lays out exactly as when shaped whole. Paragraphs with right-to-left text, bidi controls or tabs are shaped whole.
- A decorated input keeps its glyph commands between frames: moving the caret, selecting and scrolling no longer place every glyph again. Its rows find their clusters with sorted lists instead of ordered maps.

## 0.51.2 — 2026-10-26

Fixes:

- What the code that mounts a component puts on the element `mount` returns was lost when that component rendered again by itself. `ctx.mount::<C>(props).id("x")` (or `Markdown::mount(ctx, props).id("x")`) put the id on the component's root in the parent's rendered tree only; a dirty refresh of just that component (its own signal, or a theme or breakpoint change it reads) swapped its fresh render into the window without it, so `Tree::get_element_by_id` and MCP `lurq_find_by_id` no longer found the component until the parent rendered again. The same happened to a `.key(..)`, `.class(..)` or `.classes(..)` put there, and to what a `Draggable` (drag handlers, element ref, payload) or a `DropZone` (drop handler) puts on a child component's root: dragging such a component, or dropping on it, stopped working after it rendered by itself. A component's root now records what was put on it after `mount` returned, and its fresh root takes that over wherever it replaces the old one: in the window's tree and in the kept trees of the clean components above it. The outer id and key win over the component's own, as when the parent renders; outer classes are added to the component's own. The parent does not render again for this, and a parent that renders again without the decoration drops it. Kept: those four `Element` methods and what `Draggable` and `DropZone` put on their child, which is all that can be put on a mounted component's root from outside lurq. Not covered, as it is not put on the component's root: what a `DragContainer` puts on the draggables nested in its child (it rewraps their drag start to keep them in its bounds) and the `selectable` flag a selectable `Markdown` sets on the nodes of the components it mounts.

## 0.51.1 — 2026-10-23

Fixes:

- On Windows, a precision touchpad's slanted swipe still nudged a code block (or any `ScrollHorizontal`) under the pointer sideways while the page scrolled. winit delivers `WM_MOUSEWHEEL` and `WM_MOUSEHWHEEL` as separate events, one with a vertical delta and one with a horizontal, so 0.51.0's rule, which compares the two deltas of one event, never saw a slant. A horizontal-only delta is now weighed against the vertical delta seen within the last 150 ms at the same pointer (within 8 logical pixels): while that vertical delta dominates, a `ScrollHorizontal` takes none of it and the event goes to the containers around it. A mouse's Shift+wheel, with no vertical wheel just before it at that spot, a deliberate sideways swipe, and a horizontal burst after the window has passed scroll the block as before; macOS, which sends both deltas in one event, is unchanged. `Tree::set_animation_clock` (hidden, for tests) now also sets the clock this window is read on.
- A Markdown code block's box and scroll node were keyed by the hash of the block's first line, so a one-line block that was still streaming changed its key with every token: its scroll reset, a selection in it was dropped, and its node ids and MCP refs churned. They are now keyed by the block's ordinal among the document's code blocks and its language, which hold while the block streams and while paragraphs are added or removed around it. A code block inserted above a scrolled block, or removed from above it, now shifts the ordinals, and the blocks after it take the scroll of the block that had their ordinal (0.51.0 kept each block's scroll in that case, by its first line).
- MCP `scroll_to` on an element larger than its scroll container's viewport left it where it was when its start was inside the view by less than the 8 px margin. The start is now brought at least the margin inside the view; an element whose start already is stays put. (This and 0.51.0's change, which shows such an element's start instead of its end, are the only behaviour changes to `scroll_to`.)
- The headings of the 0.50.0 and 0.49.1 entries below, which the 0.51.0 release renamed to 0.51.0 by mistake, read their own versions again.

## 0.51.0 — 2026-10-23

Behaviour changes:

- A Markdown code block whose lines are wider than its box scrolls sideways inside it. Its lines stay unwrapped, as written; the box, its language label and the document keep their width, so the block never makes the document wider; and a horizontal scrollbar shows over the box's bottom padding while the block overflows, as lurq's other scroll containers show theirs. Shift+wheel and a trackpad's sideways swipe scroll it, from the innermost scroll container outward as any scroll does; a plain vertical wheel over the block scrolls the page or list around it, not the block, so a chat's follow-to-end is not caught by a block that only overflows sideways. A block whose lines fit shows no bar and lays out exactly as before, in a filling and in a fitted (`fit_content`) document, nested in a list or a quote too. Selection and copy cross a scrolled block as any block, the lines out of view included, and the block's scroll is kept when the document renders again (a streaming reply keeps its place). Before, the lines were laid out at the box's inner width and a long line was painted past it and clipped, out of reach. A math block (`$$`) is a code block and scrolls the same way. Each block's box and scroll node are keyed by the first line of its code, so a block keeps its scroll when the document renders again with a block inserted above it, a block removed, a label added or a reply streaming on (unkeyed nodes are paired by position). As with every scroll container, a Shift+wheel over a block that is at its start edge (or its end, for the other direction) is consumed by nothing and no longer reaches `on_scroll` handlers on the containers around it; and an MCP client sees each code block as an interactive scroll node in the tree, between the box and its lines.
- A scroll container that scrolls sideways only (`ScrollHorizontal`) takes no part of a mostly vertical gesture: when a wheel or trackpad delta has `|dx| < |dy|`, the container leaves the whole delta to the containers around it instead of taking its `dx`, so a chat's slightly slanted swipe scrolls the chat and nudges no code block under the pointer. A mostly sideways swipe and Shift+wheel (a delta on x alone) scroll it as before, and a mostly sideways swipe's `dy` still goes to the container around it. `ScrollVertical` and `ScrollBoth` are unchanged.
- Breaking for struct literals: `ThemeMarkdown` gains the field `code_block_scrollbar` (`ThemeMarkdown { .., ..ThemeMarkdown::default() }` is unchanged). A code block's box is now a column without padding around a padded label and a padded horizontal scroll container of the lines; the padding, the words' places and the box's size are the same, but an element lookup that counted on the lines being the box's direct child sees the scroll container between them.

Fixes:

- MCP `scroll_to` on an element larger than its scroll container's viewport (a code block's line wider than its box) scrolled the container to the element's end. It now shows the element's start, as `scroll_into_view` does, and leaves an element whose start is already in view where it is.

Added:

- `ThemeMarkdown::code_block_scrollbar: Option<ScrollBarStyle>`: the horizontal scrollbar of a code block that overflows, drawn over the box's bottom padding. The default is a thin light bar (`ScrollBarStyle::thin()` with a `#94a3b8` thumb at half opacity, inset 4 px from the bottom and 6 px from the corners) for the default dark box; `None` draws the app theme's scrollbar, always as an overlay: a `Reserved` placement is not reserved in a code block, so a block whose lines fit keeps its size.
- `ScrollBarStyle`, `ScrollBarVisibility` and `ScrollBarPlacement` implement `Debug` and `PartialEq`, so a theme holding a bar compares.

## 0.50.0 — 2026-10-22

Behaviour changes:

- A `VirtualizedList` bootstraps from where it opens. Before it has measured a row it cannot size its window (the viewport is not laid out yet), so its first pass renders a fixed number of bootstrap rows whose heights seed the estimate the next pass sizes the window with. It rendered its first 64 rows, from the top, whatever the list was asked to open on, so a chat opened at its end (`scroll_to_bottom_pending` on its `ScrollState`) built and laid out its 64 oldest turns before rendering its newest, and did so again whenever another conversation was swapped in under it (no key survives, so the heights were cleared). It now renders 16 rows (`.bootstrap_rows(n)` sets another number), taken from the end when a scroll to the bottom is queued, from the `reveal_key`'s row when there is one, or else from the top. A list opened at its end builds its last 16 rows and none from its top, the same work for 300 rows and for 3,000; its first rows are built when they are scrolled to. When those rows are shorter than the viewport, the queued scroll is kept until the window is sized from their measured heights, so the list still lands at its end. A list opened at its top renders its first rows, as before, 16 instead of 64: a list of short rows fills its viewport one frame later than it did, and passes a larger `bootstrap_rows` if that frame matters. A list opened at an offset (a queued `set_scroll_pending`, or the offset a scroll state shared with the list before still holds) renders its first rows too, since no height names the row at that offset yet, and is scrolled to the offset once they are measured, again while the content sized from the estimate grows past it as the rows at its end are measured; it used to be clamped to the bootstrap rows and, as that was their end, follow to the real end. A scroll of the person's in between stands, and items swapped in with all-new keys drop the offset the list was still restoring for the rows before (one the app queued for the new rows stays). When the items are swapped for others whose keys all differ, the measured heights go but their average stays as the estimate, so the new rows are windowed where the list opens, about a viewport's worth, instead of bootstrapped from the top again.
- A context provided in `render` renders again only the descendants that read it. A component renders again for a context when a value of a type it read (`use_context`, `consume_context`, in `create`, a render or a handler) is provided anew, or when its own render provides values, since only a render provides them again; every other component keeps its rendered tree and passes the contexts on, so a reader below one renders in place with the pass and sees the new value; a `for_each` item that read the value (or provides) is rendered by its owner, whose render holds its closure. A component providing values in its render used to render every descendant again, read or not. `Tree::get_element_by_id`, `get_element_by_id_mut`, `get_elements_by_class_name` and the MCP element tree flush such readers too, refreshing again while a refresh replaced something (up to the eight refreshes a pass makes), so a lookup between passes sees the settled subtrees. `provide` still compares nothing: each call is a new providing, and the readers of that type render again; `Ctx::provide_if_changed` keeps the earlier providing while the value is equal (`PartialEq`), so nothing renders again for it.

Fixes:

- A `Markdown` document with a link in it kept the window's layout dirty: every idle pass found it dirty and laid the window out again, for as long as the document was shown (a chat showing a reply with a link relaid its window on every frame, ~2–3 ms in release). A link's node is placed by its paragraph's layout and holds no layout of its own, so the marks that ask for its layout (its anchor's attachment, a hover or focus style) were never consumed; the paragraph's layout now consumes them. A document without a link settled as before, and one with a link settles with it; a hovered link whose style keeps its metrics is painted, not laid out again.

Added:

- `VirtualizedList::bootstrap_rows(n)`: how many rows the list renders before it has measured one (16 by default).
- `Ctx::provide_if_changed(value)`: `provide`, unless the value equals the one this component provided before (`PartialEq`), in which case the descendants that read it see the same providing and do not render again. In `render` the value is compared with the previous render's; in `create` or a handler, with the one provided there.

## 0.49.1 — 2026-10-21

Behaviour changes:

- Hover follows content that moves under a pointer that holds still. After every layout that changed (a wheel scroll, a list that grew, a stick-to-bottom chat taking a message, any relayout), lurq hit-tests the hover again at the pointer's last position, like a browser: `on_mouse_enter`, `on_mouse_leave`, `hovered` styles and the cursor now change without a mouse event, in the frame that shows the new layout, and the winit shell applies the cursor after each frame. The handlers run with the source of the input that last moved the pointer, so an agent's pointer stays synthetic input. Nothing is hovered while the pointer is outside the window or a drag holds it, and a click held back for a double click no longer re-hovers what was under it after the pointer moved on or left.
- A hover style that moves its own node away from a still pointer (a `hovered` size, offset or transform, with or without a transition) unhovers the node, which moves it back under the pointer, which hovers it again: like CSS `:hover`, such a node flickers, now also while the pointer holds still. Keep hover styles from moving the node off the pointer.
- An anchored overlay (`Overlay`, `Popup`, a Markdown link's tooltip), a `Select`'s menu and a `Modal` over an element are not drawn while their anchor (the select, the target element) is scrolled or clipped wholly out of view, and come back with it. Their open state is kept, and such a hidden popup is dismissed like a CSS popover that is out of view: a left press anywhere closes it (with `dismiss_on_outside_click`) and is not consumed, so it also reaches what it lands on; Escape closes it (with `dismiss_on_escape`); and keyboard focus inside it goes back to its anchor, or the first focusable element inside the anchor, or else the nearest focusable ancestor of the anchor. A tooltip with no open signal just stays hidden.

Fixes:

- A tooltip shown on hover stayed on screen when the content scrolled under a pointer that held still, and was drawn over the header above the list, away from its link, which had scrolled under that header (a Markdown link's tooltip in a chat). Hover was hit-tested only on mouse events, so the link never got its `on_mouse_leave`. See the first behaviour change.
- An anchored overlay (a Markdown link's tooltip shown for keyboard focus, an open `Popup`) and a `Select`'s menu followed their anchor out of a scroll container's viewport and were drawn over whatever covered the anchor, such as the header above a list. See the third behaviour change.

## 0.49.0 — 2026-10-20

Behaviour changes:

- A paste shortcut delivered as synthetic input (an MCP client's `lurq_interact` `key` of `Ctrl+V`, `Cmd+V` or `Shift+Insert`, an applied `SyntheticInput::key_down`) no longer reads the OS clipboard: the person's clipboard is theirs, and an agent driving the window must not paste from it silently. The shortcut is refused and inserts nothing. A synthetic paste carries its own content instead: `SyntheticInput::paste(content)`, or the MCP `paste` action with `text` and/or `files`. A person's `Ctrl+V` pastes as before.
- An `Image` node's pixels are placed by its `fit`: `Stretch` by default, which draws as every image drew, so nothing changes unless `Image::fit`, `contain()` or `cover()` is called.
- Breaking for exhaustive matches and struct literals: `SyntheticInputKind` gains the variants `Paste`, `FileDragEnter`, `FileDragOver`, `FileDragLeave` and `FileDrop`, and `EventHandlers` the fields `on_file_drag_enter`, `on_file_drag_over`, `on_file_drag_leave`, `on_file_drop` and `on_paste`. Every other existing API is unchanged.

Added:

- Clipboard images and files (feature `clipboard`): `lurq::clipboard::read_clipboard() -> Option<ClipboardContent>` reads everything the clipboard holds at once, the text, the image a screenshot tool or a browser put there (Windows `CF_DIBV5`/`CF_DIB`, macOS `public.png`/`public.tiff`, read through `arboard` as RGBA) and the files copied in Explorer or Finder (`CF_HDROP`, file URLs); a clipboard may hold text and an image together, and `ClipboardContent::kinds()` tells which. `ClipboardImage::to_png()` encodes an image to store it (through the `png` crate, which `image` already pulled in); `ClipboardImage::from_rgba(width, height, rgba)` checks the size and bytes of one built by hand. `copy_image_to_clipboard(width, height, &rgba)` and `copy_files_to_clipboard(&paths)` write the other way. `ClipboardContent`, `ClipboardImage`, `ClipboardKinds` and `ClipboardImageError` live in `lurq::app::events` and are built without the feature, so a headless test pastes without an OS clipboard; the text functions are unchanged.
- A paste event on text inputs: `on_paste(|PasteEvent| …)`, on the input or on an ancestor it bubbles to, runs before the default inserts the text. `Ctrl+V` (`Cmd+V` on macOS), `Shift+Insert`, `WindowHandle::paste_from_clipboard()` (for an app's own Paste menu item or context menu; feature `clipboard`) and `Tree::paste(content)` all go through it. The event carries the `ClipboardContent` (`text()`, `image()`, `files()`, `kinds()`, `content()`), its `target_id` and the `input_id`; `prevent_default()` keeps the text out of the input, `stop_propagation()` ends the bubbling. So an app takes an image or files and stops the insertion, turns a long text into an attachment, or lets plain text paste as it always did. The handler runs inside the input's delivery, so `is_synthetic_input()` tells an agent's paste from a person's. The clipboard is read as far as the paste needs: a paste no `on_paste` handler looks at reads only the text, as before; one a handler looks at reads the image and the files too. A `paste_from_clipboard()` request made while lurq delivers synthetic input (an MCP client's click on the app's Paste menu item) is refused by the shell (`Tree::paste_from_os_clipboard(synthetic)`), like a synthetic shortcut.
- Files dragged into the window from the OS (Explorer, Finder) reach the element under the pointer, with overlays and modals hit-tested as for the mouse: `on_file_drag_enter(FileDragEvent)` once when the drag comes over the element, `on_file_drag_over(FileDragEvent)` on every move over it (`x`, `y` in logical pixels), `on_file_drag_leave()` when it moves off or leaves the window, and `on_file_drop(FileDropEvent)` on the drop; enter, over and drop bubble to the ancestors. `event.paths` (`DraggedPaths`) is given once for the whole drag, however many files it holds, and reports folders as folders (`files()`, `folders()`, `has_folders()`, `DroppedPath::is_folder()`), looked up once; text or an image dragged from a browser is ignored, since winit reports nothing for it. A `drag_over` state style (`.drag_over(|style| …)`, `drag_over_style`, `InteractionState::is_drag_over()`) applies while the drag is over the element, like `hovered`. `event.refuse()` on an enter or over event refuses the drag at the element whose handler called it, not at its ancestors or siblings, for as long as the drag stays over it: no element shows the style and `Tree::file_drag_accepted()` reports `Some(false)`, and leaving and entering the element again asks again; the OS cursor is not changed, since winit answers the OS with a copy effect before lurq sees the drag, and the drop is still delivered to `on_file_drop`, whose handler ignores what it refused. A shell drives it with `Tree::file_drag_enter(paths, x, y)`, `file_drag_over(x, y)`, `file_drag_leave()` and `file_drop(paths, x, y)`; the winit shell collects the OS's burst of one event per file into one session on Windows and macOS and reads the pointer from the OS every 16 ms while the drag hovers (`GetCursorPos`, `NSEvent::mouseLocation`), delivering `on_file_drag_over` when it moved, because the OS owns the pointer during a drag and winit reports no position; a hover ends as a leave when no mouse button has been pressed for 250 ms of polls with no file event in between (the OS drag ended without winit telling; `GetAsyncKeyState` on Windows, `NSEvent::pressedMouseButtons` on macOS; the grace period covers the release, which the OS reports before its drop callback, so a drop within it continues the session without a leave) or when it neither moved nor got a drop or a cancel for 60 s, since its source is gone and polling would never stop. On Linux the last pointer position the window saw is used. Secondary windows take drops too.
- Images decoded at runtime (feature `image`): `Image::from_bytes(bytes)`, `Image::from_file(path)` and `Image::from_source(source, key)` build a node that worker threads decode off the UI thread (PNG, JPEG, the first frame of a GIF or WebP, BMP, TIFF). The node shows its `.placeholder(element)` and its own background until the pixels are there, then the image, and the `.error_view(|error| …)` built from the `ImageDecodeError` for a broken file, never a panic. `.downscale_to(width, height)` caps the decoded size, keeping the aspect ratio and never upscaling, so a thumbnail of a 4K screenshot does not keep its 30 MB of RGBA. `.fit(BackgroundSize)`, `.contain()`, `.cover()` and `.stretch()` place the pixels in the box of any image node. Decoded pixels are kept in the process-wide cache `lurq::images::decoded_images()` (`DecodedImages`), keyed by content and size cap: `from_bytes` hashes the bytes (`ImageKey::of_bytes`), `from_file` keys the path with the file's size and modification time (`ImageKey::of_path`), and `Image::from_source(ImageSource::Bytes(arc), ImageKey::new(hash))` takes a hash the app stores without hashing or copying the bytes (`.cache_key` replaces the key after `from_bytes` has hashed). A chat laid out again, or a `VirtualizedList` row built again as it scrolls, finds its image ready in the first pass and decodes nothing. The cache keeps at most `budget()` bytes of RGBA (`DEFAULT_BUDGET_BYTES`, 128 MiB; `set_budget`), dropping the least recently used ready images; an image larger than the whole budget on its own, decoded or inserted, is still shown and leaves the cache at the next eviction while the node showing it keeps its pixels; `state(key, cap)` reads an entry, `insert` puts pixels the app decoded, `wait_idle(timeout)` and `lurq::images::wait_for_decoded_images(timeout)` block until no decode is pending, `DecodedImages::new()` makes a cache of a test's own, and `decode_image(&source, cap)` decodes on the calling thread. The decode's end wakes the window's loop, so the image is drawn without the app doing anything.
- Headless helpers: `SyntheticInput::paste(content)`, `file_drag_enter(paths, x, y)`, `file_drag_over(x, y)`, `file_drag_leave()` and `file_drop(paths, x, y)` reach the same entry points as the shell, marked synthetic; `Tree::set_clipboard_reader(Some(Arc<dyn ClipboardReader>))` installs a clipboard of a test's own for a person's `Ctrl+V` (`lurq::app::ClipboardReader`: `read_text()` for a paste no handler looks at, `read()` for one an `on_paste` handler looks at), so a test never touches the OS clipboard; `DraggedPaths::from_paths` and `DraggedPaths::new([DroppedPath::with_kind(path, is_folder)])` build the paths of a drag, and `ClipboardContent::text`, `image`, `files` with `with_text`, `with_image`, `with_files` the content of a paste.
- MCP `lurq_interact` actions: `paste` (`text` and/or `files`, delivered to the focused text input and its ancestors' `on_paste` handlers), `drag_files` and `drop_files` (`paths` over or onto a `ref` or point, as an Explorer or Finder drag), and `file_drag_leave`.
- `Tree::has_file_drag()`, `Tree::file_drag_paths()` and `Tree::file_drag_accepted()` report the drag over the window.

## 0.48.2 — 2026-10-20

Fixes:

- A single-line text with an ellipsis (`TextOverflow::Elipsis`, `nowrap`) and a shrink factor in a Row or Column beside a growing child (a `Spacer::flex(1.0)`) was cut although its words fit, with the free room still beside it: "Pausing run #4 of KON-10 · dismiss…" in a box 1/16000 px narrower than its words. The line granted the growing child the room left and then summed its children back up to find the overflow to shrink by; in `f32` the sum could come out a few micro-pixels over the line, and the text was laid out again that much narrower and ellipsized, since a text over its box by any amount is cut. Whether it happened depended on the fractions of the line's width and of its texts' widths (a time in a label, a title's words), so most titles of a kind were fine and some were cut at some window widths. The overflow of a line now counts the free room its growing children fill once, as it was granted: the children sized on their own, a flex basis, and what a child takes beyond its grant are what can overflow the line. A row too narrow for its words still ellipsizes them.

## 0.48.1 — 2026-10-17

Fixes:

- Inline code and code blocks in Markdown are drawn in a monospaced font. The default Markdown theme, `ThemeFonts::mono` and the devtools ask for the family `"monospace"`, and a family name was always looked up as a font of that name: there is none, so that text was drawn in the fallback font, proportional (Segoe UI on Windows, DejaVu Sans or Lato on Linux). A `font_family` that is a CSS generic family (`"serif"`, `"sans-serif"`, `"monospace"`, `"cursive"`, `"fantasy"`, in any ASCII case) now asks for the platform's font for it (Consolas on Windows, Menlo on macOS, DejaVu Sans Mono on Linux for `monospace`; `GenericFamily` lists them all), in plain text, rich text and Markdown spans, text inputs and canvas text, for measuring, painting, carets and selection alike. `sans-serif` draws as the empty family does. The fonts are chosen when the `App` is created; to draw a generic family in a bundled font, load it and register an alias of the keyword (`app.register_font("monospace", "JetBrains Mono")`), which is still resolved first, and any other name is still a font's. With the default Markdown theme, table header cells, table cells, table markers and the code block's language label are styled from inline code too, so they become monospaced as well. Code and table text is wider than before, so Markdown with code or tables wraps and measures differently.

## 0.24.2 — 2026-09-25

- Fix a UI-thread hang when a callback writes the signal it observes. `Signal::set` and `Signal::update` called the signal's subscribers while holding its value and subscriber locks. So a `ctx.watch` callback that set its own signal never returned, and neither did subscribing to or dropping a subscription of that signal from a callback. A common case was restarting a `FutureAction` from a watch on its own state: the completion set the state, the watch called `run`, and `run` set the state to `Pending`. Cooperative (non-Tokio) futures hung a second time, because `AsyncTask` was polled while holding the task lock that `run` takes. A notification now holds no lock while it calls observers, and the task lock is released before polling.
  - Writes from callbacks follow one rule. The value changes at once, and the notification comes after the current one. Every observer first receives the current value, then all of them are notified again with the latest value. Several writes during one notification produce one more notification. Writes from other threads during a notification are delivered by the thread that is already notifying. A watcher added during a notification starts with the next one. A watcher dropped during a notification is not called again.
  - Effects rerun when they write a signal they read, including during their first run. Before, such writes were missed. An effect never reruns inside its own run.
  - `set` still does not compare values. A callback or effect that writes its own signal on every notification is stopped after 100 consecutive self-caused notifications, and the triggering write panics with the signal or effect id. The signal keeps working afterwards.
  - Inside a `ctx.watch` callback, `update` on the watched signal panics instead of hanging, because the callback still borrows the value. Use `set` there. `update` still works on other signals and from effects and memos.
  - A notification no longer copies the watcher list into a new `Vec`; observer lists are copy-on-write. A signal's value now sits behind an `Arc`, which costs one extra allocation per signal. `set` allocates only when a notification still borrows the old value.
  - The Reactivity guide documents writes from callbacks.

The default minimize color changes from `#ffbd2e` (the pre-Big Sur value) to `#febc2e`, matching the macOS 11+ close `#ff5f57` and zoom `#28c840` lurq already used. Apple does not publish these colors; they are sampled from the system controls.
- Stop resize handles from shrinking the content area. The new `ResizeHandlePlacement` (`WindowChromeProps::resize_placement`, `WindowChrome::resize_placement`) defaults to `Overlay`: the invisible edge and corner hit zones cover the outermost pixels of the content, which now fills the window below the title bar. Before, content and overlays were inset by the handle size on the left, right, and bottom, so a 1440-wide window gave 1434 px of content. `ResizeHandlePlacement::Inset` restores that layout. `WindowChromeMetrics::resize_inset` returns 0 for `Overlay`; the new `resize_handle_size_for(WindowInfo)` returns the active hit-zone size.
- Hide the Windows 11 compositor border around custom chrome. DWM draws a 1px border around undecorated windows, so a `WindowChrome` with `ChromeBorderPolicy::Hidden` still showed an outline. Add `WindowBorderColor` (`Default`, `None`, `Color`) with `WindowHandle::set_border_color` and `border_color`, mapped to `DWMWA_BORDER_COLOR` by the winit shell on Windows 11 build 22000+ and ignored elsewhere. `WindowChrome` sets `WindowBorderColor::None` when custom chrome is active; the frame outline comes only from `ChromeBorderPolicy`.
- Fix a faint 1px line on every window edge (and a soft 2px edge on every rect). The quad shaders (wgpu and DX12) average four half-pixel subsamples but gave each one a full-pixel anti-alias ramp, so a pixel entirely inside an axis-aligned edge got 87.5% coverage and the pixel outside got 12.5%. A window-sized root rect therefore let the clear colour show through its outermost pixels, maximized or not. Each subsample now uses a half-pixel ramp: pixel-aligned edges are exact, and curved and fractional edges stay anti-aliased. Rect edges throughout the UI render slightly crisper.
- Resolve the frame clear colour through the theme and past the overlay host. It was the root node's concrete background only, so a palette-coloured root, or any root while a `Modal`/overlay was mounted (which includes every `WindowChrome`), cleared to white.
- Fix live window resizing on Windows from custom chrome. Dragging a resize handle stretched the last frame for the whole drag, then froze the app for up to several seconds before it drew the new size. The shell started the native sizing loop with a synchronous `SendMessageW`, so the loop ran inside the lurq event handler, where winit queues every event. No frame was drawn during the drag, and afterwards the wgpu engine reconfigured its surface once per queued size event, which took about 2.4 ms each in a debug build. Now the shell posts the non-client press, at the real cursor position instead of (0, 0), so the loop runs from winit's pump. A `Resized` for the window's current size is painted immediately; WM_PAINT is starved during the loop. `WgpuRenderEngine::resize` records the size, and the next frame reconfigures the surface once. `start_drag` uses the same path. Present since custom chrome was added, not a regression.
- Breaking: `WindowChromeProps` and `WindowChromeMetrics` struct literals need `resize_placement` or `..Default::default()`.

## 0.20.0 — 2026-09-17

- Add gradient paints to `Context2D` fills and strokes: linear, radial and angular, 2 to 16 stops, with a centre, a size and a rotation normalised to a box. A gradient is a fragment-shader paint — one 256-texel ramp per distinct stop list, and paint coordinates carried in the vertex `uv` solid paths leave unused — so the mesh-cache key and the per-batch vertex charge are unchanged. An unusable gradient draws nothing rather than a colour of its own choosing, and is refused for shaped text with `UnsupportedPaint`.
- Add outer and inner shadows (`set_shadow`) and a `filter`-like layer blur (`set_filter`) to fills, strokes and shaped text. Both are rasterised once on the CPU into a premultiplied image and drawn like any other image, so the software backend and both native backends share one implementation. Bounded by a reduced raster for wide blurs, clipping to the surface, `MAX_EFFECT_PIXELS`, and 512-unit caps on blur and spread; rasterisations are cached process-wide at 32 MiB with random eviction. Offsets, blur and spread are in user space and scale with the transform, unlike HTML Canvas.
- Add eighteen blend modes through `set_global_composite_operation`, and isolated group compositing through `begin_layer(alpha, blend)` / `end_layer`, which is what makes a group of overlapping shapes fade as one image. Layers nest to `MAX_LAYER_DEPTH`, hold their commands on the surface until they close, and cost the renderer two shared tile-sized textures per open depth rather than a surface-sized target.
